# MoaSearch 개발 설계

## 목표와 실행 방식

Windows PC의 선택한 폴더 또는 드라이브를 재귀적으로 색인하고 파일명, 본문, 의미로 검색한다. 파일 원본을 수정하지 않는다. 웹 UI는 127.0.0.1에만 바인딩되는 로컬 앱이며 외부 서비스로 파일을 전송하지 않는다.

사용자 요구에 따라 Ollama에 의존하지 않는다. 앱 프로세스가 관리하는 llama-cpp-python 엔진이 로컬 GGUF 모델을 직접 실행한다. 임베딩과 답변 생성 모델은 별도로 설정한다. 엔진 또는 모델이 없으면 키워드 검색은 계속 동작하며 의미 검색 준비 상태를 명시한다.

## 데이터 흐름

폴더 등록 → 안전한 순회 → 파일 메타데이터 → 형식별 텍스트 추출 → 위치를 보존한 청크 → SQLite FTS5 + 임베딩 저장 → 키워드/코사인 유사도 결합 → 파일별 결과 및 출처 → 선택적으로 로컬 LLM 답변.

SQLite에 폴더, 파일, 청크, 벡터, 설정을 보관한다. 모델 식별자를 벡터와 함께 저장해 다른 모델의 벡터를 혼합하지 않는다. 파일 크기·수정 시각을 비교하여 변경 파일만 다시 처리한다. 모델 준비 후 재색인하면 누락된 임베딩을 채운다. 정상적으로 순회한 폴더에서만 삭제 파일을 정리한다.

## 범위와 제한

- 파일명 검색: 등록한 경로에서 접근 가능한 일반 파일. 시스템·캐시·자격증명 경로 및 재분석 지점/심볼릭 링크는 기본 제외.
- 본문 검색: 텍스트, 코드, 디지털·스캔 PDF, DOCX, XLSX, PPTX, 지원하는 OpenDocument, HWP5/HWPX. PDF는 pypdfium2 내장 PDFium으로 최대 250페이지를 읽는다. 텍스트층을 우선하며, 텍스트가 없고 이미지 등 페이지 콘텐츠가 있으면 OCR한다. 문자·숫자가 40자 미만이고 이미지 객체가 있는 페이지도 OCR하여 혼합 문서를 처리한다. 페이지는 최대 200 DPI로 렌더링하며 긴 변 3200픽셀 또는 8MP를 넘으면 축소한다. 이미지(PNG/JPEG/BMP/TIFF/WebP)도 같은 OCR 모델로 읽는다.
- 오디오 전사·검색과 영상 분석은 미지원이며 파일명·경로로 검색한다. 구형 HWP3, 암호화·배포용 HWP/HWPX의 본문은 지원하지 않는다. OCR은 한국어·영어 인쇄 글자를 대상으로 하며 손글씨·도형 인식 정확도는 보장하지 않는다. 이미지 한도는 원본 최대 100 MiB, 프레임당 40 MP(긴 변 최대 4096), 파일당 16프레임이다. PDF 한도는 100 MiB·250페이지이며 전체 파일 기본 크기 한도는 32 MiB(설정 최대 512 MiB), 지원 문서 추출은 파일당 200,000자까지다. PDF 색인 취소는 진행 중인 네이티브 페이지 렌더링/OCR이 끝난 뒤 다음 페이지 전에 반영한다.
- 벡터 검색은 SQLite의 모델·차원·변경 버전으로 구분한 정규화 행렬을 최대 128 MiB까지 재사용한다. 한도를 넘으면 256개 벡터씩 정확 비교하고 결과 파일 수만큼의 최소 힙을 유지한다. 수백만 청크 환경은 ANN 벡터 인덱스와 별도 벤치마크가 필요하다.
- 파일별 본문/파일 크기 한도 및 제외 경로를 적용한다. 읽기 실패는 파일별로 기록하며 전체 작업을 중단하지 않는다.
- 원본 문서는 신뢰하지 않는 검색 자료로 취급한다. LLM은 도구 호출·파일 실행·자동 변경 권한을 갖지 않는다.

## 개발 단계

1. 프로젝트 골격 및 로컬 저장 구조.
2. 문서 추출, 증분 색인, 키워드 검색.
3. 내장 GGUF 엔진, 의미 검색 및 근거 기반 답변.
4. 한글 로컬 UI, 실행 도구, 통합 검증 및 사용 안내.
5. HWP5/HWPX 본문 파서와 보호·손상 문서 검증.
6. 한국어·영어 이미지 OCR과 고정 ONNX 모델 관리.
7. 기존 색인 갱신, OCR 설정 화면, 형식별 검색 통합 검증.
8. PDFium 페이지 렌더링과 선택적 스캔 페이지 OCR.
9. 페이지별 OCR 진행, 부분 실패 보존, 취소와 재색인 통합.
10. 혼합·스캔 PDF의 추출, 키워드·의미 검색 재현 검증.
11. 대량 파일·벡터 성능 기준과 재현 벤치마크.
12. DB 연결 재사용, 배치 저장, 트랜잭션별 카운터·변경 버전.
13. 벡터·질의 캐시, 본문·파일 경로 조회 인덱스, 정확 검색 유지.
14. 최종 성능 비교와 실제 모델 회귀 검증.

각 단계는 관련 검증 후 한글 커밋 메시지로 기록한다.

## 대량 색인과 검색

색인 작업의 SQLite 연결을 재사용한다. 완성된 파일을 최대 32개, 256청크, 약 4 MiB 기준으로 모으고 0.5초 경과를 파일 사이에서 확인해 저장한다. OCR·임베딩 중에는 쓰기 트랜잭션을 유지하지 않는다. 하나의 큰 파일은 완전히 읽은 뒤 저장하며, 취소 시 진행 중인 파일을 제외하고 완료된 파일만 반영한다.

`index_meta`의 파일·청크·벡터 수와 변경 버전은 트리거로 원본 변경과 함께 커밋된다. 다른 프로세스가 색인해도 검색 캐시는 DB 읽기 스냅샷의 버전으로 교체된다. 상태 조회는 전체 행을 세지 않는다. 파일 경로 FTS5와 본문을 포함하는 조회 인덱스는 짧은 검색어 조회가 벡터 BLOB까지 읽지 않도록 돕는다. 보조 인덱스만큼 디스크 사용량은 늘어난다.

모델별 최근 질의 임베딩은 최대 64개, 벡터 스냅샷은 하나만 보관한다. 확장자 필터, 파일별 최고 청크, 점수 동률 순서를 유지하며 상위 본문은 한 번의 SQL로 조회한다. 근사 검색은 사용하지 않는다. 측정 조건과 한계는 [성능 기록](performance.md)에 남긴다.

## 구현 검증

기본 엔진은 공식 CPU wheel의 llama-cpp-python 0.3.36이다. Qwen3-Embedding-0.6B Q8_0과 Qwen3-0.6B Q8_0을 앱에서 다운로드하고 고정 SHA-256으로 검사한다. 임베딩·대화 모델을 번갈아 메모리에 로드하며 추론 호출은 직렬화한다. OCR은 별도 PP-OCRv5 ONNX 모델 두 개(약 18.3 MB)를 첫 설치 때 내려받고 CPU에서 추론한다. PDF는 텍스트를 먼저 추출하고 OCR이 필요한 페이지만 최대 200 DPI로 렌더한다. PDFium 렌더 호출은 스레드 안전성 제약에 따라 직렬화하고 페이지·픽셀·문자 수를 제한한다. 일부 페이지 OCR이 실패해도 정상 추출한 PDF 텍스트는 키워드 검색용으로 저장하고, 파일 오류를 기록해 다음 색인에서 다시 시도한다. 취소는 현재 PDF 페이지의 네이티브 렌더링/OCR 작업이 끝나면 다음 페이지 전에 반영한다. 파일 본문 추출 리더 버전을 DB에 기록해 리더가 바뀌면 기존 메타데이터 행도 재추출한다. 색인 중에는 네 청크 단위로 취소 여부를 확인한다.

단위·API 테스트로 증분 색인, 취소, 접근 실패 보존, 임베딩 모델 분리, OCR/HWP 내용 추출과 다운로드 검증, 외부 Origin/Host 및 토큰 차단을 확인한다. 별도 실제 GGUF 검증은 저장소의 가상 문서 세 개만 사용하며 한글 의미 검색 3개와 인용 답변을 확인한다. `scripts/smoke_ai.py`로 재현할 수 있다.

`scripts/smoke_pdf.py --model-dir <모델 폴더>`는 가상 한국어 스캔·혼합 PDF를 생성해 네트워크 요청을 차단한 상태에서 실제 OCR, 페이지 번호, 키워드·의미 검색과 증분 색인 재사용을 검증한다. PDFium 렌더러는 회전·픽셀 한도·예외 시 자원 해제를 별도 단위 테스트로 확인한다.

실행 프로세스는 원본 파일을 읽는 권한만 사용하며 관리자 권한을 요구하지 않는다. 웹 UI가 파일 열기를 요청할 때 현재 등록된 범위와 실제 경로를 다시 확인하고, 실행 파일과 스크립트는 열기 대상으로 허용하지 않는다. 로컬 색인 DB에는 추출한 본문이 저장되므로 앱 데이터 폴더는 사용자 계정의 접근 권한으로 보호해야 한다.
