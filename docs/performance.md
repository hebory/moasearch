# 대량 파일 성능 기록

## Rust 전환 후 측정

2026-11-12, 같은 Windows PC에서 Rust 1.97.1 MSVC의 release 빌드로 측정했다. 가상 텍스트 파일 5,000개에서 20,000청크·384차원 결정적 가짜 벡터를 생성했다. 모델 추론·모델 로드·OCR 시간은 제외한다. 아래 Python 측정과는 색인 문서 길이와 임베딩 생성 조건이 달라 직접적인 배속 비교를 하지 않는다.

| 측정 | Rust |
|---|---:|
| 최초 색인 5,000개·20,000청크 | 8.409초 |
| 변경 없는 재색인 | 0.284초 |
| 50개 수정 후 재색인 | 0.345초 |
| 첫 검색, 벡터 캐시 준비 포함 | 110.25ms |
| 이후 서로 다른 질의 4개의 중앙값 | 8.58ms |

최초 5,000개, 수정 후 50개만 색인했고, 변경 없는 5,000개는 모두 재사용했다. 오류는 0개이며 검색 5건의 예상 첫 결과를 확인했다. 가짜 벡터 검색 검증 질의는 파일명·문서 번호·본문 단어와 겹치지 않게 구성했다. 실제 자연어 검색 품질은 별도의 Google 모델 검증으로 확인한다.

```powershell
.\build.ps1 -PrepareOnly
cargo run --release --locked --example benchmark -- --files 5000
```

보고서는 `.moasearch-perf/run-rust-<PID>/report.json`에 저장한다. 이번 측정은 `run-rust-43812`이며 각 색인 단계 1회, 검색 5회를 실행했다. 하드웨어·저장장치·문서·벡터 차원에 따라 결과가 달라진다.

### 기능·배포 검증

- release 기본 테스트 32개와 모델을 별도로 지정하는 실제 OCR 테스트 1개를 통과했다. 경로 경계, 기존 DB 전환, 배치 원자성, 취소·증분 재사용, 정확 벡터 검색·캐시, API 인증, 한국어 문자열 처리와 포맷 읽기를 포함한다.
- Google EmbeddingGemma 2로 한국어 의미 검색 3건, Gemma 4 E2B로 문서 인용 답변 생성을 확인했다.
- 가상 문서 5개에서 HWP/HWPX 본문 검색 2건, 영수증·스캔 PDF·혼합 PDF 자연어 검색 3건을 통과했다. fixture 설명 README는 정답 정보를 포함하므로 검증 문서 집합에서 제외한다. 두 번째 색인은 5개 모두 재사용했다.
- PNG의 한국어·영어·숫자 OCR, 스캔 PDF, 손상된 표지 구조가 있는 혼합 PDF 복구, 유효한 디지털 PDF 텍스트 추출을 확인했다.
- 기존 예제 DB의 파일 9개·청크 10개·벡터 10개를 보존하고 Google 임베딩으로 다시 색인했다. 오류 0개, HTTP 자연어 검색의 첫 결과 `meeting.pdf`를 확인했다.
- Windows 기본 PowerShell의 설치 런처와 `dist/moasearch.exe` 실행을 확인했다. 앱에는 Python·Ollama가 필요 없으며 ONNX Runtime DLL 두 개를 함께 배포한다.

이 검증은 가상 문서와 CPU 실행을 대상으로 한다. 전체 PC 장기 운용, 모든 HWP/PDF 변형, 필기체 OCR, GPU 가속 또는 일반적인 답변 정확도 전체를 보장하는 벤치마크는 아니다.

## 이전 Python 측정

아래 비교표는 **Python 구현의 14단계(`7ee31b4`) 기록**이다. Rust 전환 후의 실행 속도를 뜻하지 않는다. Rust 측정은 `cargo run --release --example benchmark`로 별도 재현하며, 실제 모델 추론 시간은 이 합성 벤치마크에 포함하지 않는다.

2026-11-12, 같은 Windows PC의 일반 실행 프로세스에서 기존 버전 `8a509ab`와 개선 버전을 비교했다. 가상 텍스트 파일 5,000개, 별도 검색 색인 20,000청크·384차원을 사용했다. Python 3.12.13, SQLite 3.50.4 환경이다.

| 측정 | 기존 | 개선 후 | 기존 / 개선 |
|---|---:|---:|---:|
| 최초 텍스트 색인 5,000개 | 55.353초 | 15.988초 | 3.5배 |
| 변경 없는 재색인 | 4.599초 | 0.254초 | 18.1배 |
| 파일 1%인 50개 수정 후 재색인 | 4.976초 | 0.404초 | 12.3배 |
| 검색 캐시가 준비된 뒤 질의 중앙값 | 161.70ms | 8.35ms | 19.4배 |
| 첫 질의, 캐시 준비 포함 | 145.70ms | 175.40ms | 첫 준비 비용 증가 |
| 키워드 검색 1회 | 3.41ms | 2.20ms | 1.6배 |
| 파일명 검색 1회 | 3.23ms | 1.95ms | 1.7배 |

각 색인 과정의 오류는 0개였다. 변경 없는 재색인은 5,000개 모두 건너뛰었고, 수정 색인은 50개만 처리했다. 모든 검색 측정에서 정해 둔 의미·키워드·파일명 결과를 찾았다. 질의는 총 5개이며, 준비 후 중앙값은 첫 질의를 제외한 서로 다른 4개 질의를 사용한다. 동일 질의 임베딩 캐시의 효과로 수치를 부풀리지 않는다.

## 측정에 포함한 것

색인은 파일 읽기·본문 추출·SQLite 저장·삭제 확인을 측정하며 임베딩 모델은 사용하지 않는다. 검색은 결정적인 가짜 임베딩을 주입하여 키워드 조회·벡터 검색·파일별 순위 계산을 측정한다. 실제 LLM 추론 시간, OCR 시간, 처음 모델을 읽는 시간, 검색용 가상 벡터 생성 시간은 이 표에 포함하지 않는다.

첫 질의는 DB에서 벡터 캐시를 구성하므로 기존보다 약 30ms 길었다. 이후 질의는 해당 행렬을 재사용한다. 추가·수정·삭제가 커밋되면 캐시를 다시 준비한다. 최초 캐시 준비와 반복 검색의 시간을 따로 확인해야 한다.

위 수치는 이 PC에서 각 색인 단계 1회, 검색 5회를 측정한 결과다. 하드웨어, 디스크, 백신, 문서 크기·종류, 벡터 차원에 따라 달라진다. 측정 환경의 파일 접근 제약으로 경로 확인 비용이 늘어난 샌드박스 수치는 최종 표에서 제외했다. 검색 캐시 준비 최적화 후 검색 부분만 같은 가상 DB에서 다시 측정했다.

## 바뀐 구조

- 색인 작업에서 DB 연결을 재사용하고, 완료된 파일을 묶어 원자적으로 저장한다. OCR·임베딩 중에는 쓰기 잠금을 유지하지 않는다.
- 상태 화면의 개수는 행 전체를 세지 않고 트랜잭션 안에서 갱신한 카운터로 조회한다.
- 파일 경로의 trigram FTS와 본문 조회용 인덱스로 짧은 검색어도 큰 벡터 BLOB을 읽지 않고 확인한다. 이 보조 인덱스는 추가 디스크 공간을 사용한다.
- 모델·차원·DB 변경 버전을 키로 정규화 벡터를 재사용한다. 보관하는 배열은 기본 128 MiB까지이며, 전체 프로세스 메모리 제한을 뜻하지 않는다.
- 캐시 한도를 넘거나 메모리가 부족하면 256개씩 벡터를 읽고 필요한 상위 파일 수만 유지한다. 근사 검색으로 결과를 생략하지 않는다.
- 최근 질의 64개의 임베딩을 모델별로 구분해 재사용하고, 결과 본문은 한 번의 SQL로 읽는다.

캐시는 실행 중인 앱 메모리에만 유지한다. 앱을 다시 시작하면 첫 검색에서 준비하며, 모델이 바뀌면 이전 벡터를 섞지 않는다. 백만 개 이상의 벡터, 전체 PC 장기 색인, 대규모 OCR 문서 성능은 이번 측정 범위가 아니다.

## 이전 Python 측정 재현

다음 명령과 Python 스크립트는 `7ee31b4` 체크아웃에서만 사용한다. 현재 Rust 버전에서는 Python 런타임과 스크립트를 제거했다. 각 실행은 `.moasearch-perf/run-*`에 가상 파일과 독립 DB를 만들며 사용자 문서 폴더를 읽지 않는다.

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_performance.py --label after --files 5000 --chunks 20000 --dimension 384 --repeats 5
```

같은 스크립트와 인자로 기준 버전의 `src`를 별도 체크아웃해 `PYTHONPATH`로 지정하면 기존 버전을 측정할 수 있다. `--label`은 보고서 이름만 지정하며 코드 버전을 바꾸지 않는다. 가상 파일 생성·벡터 생성 시간은 측정 구간 밖이다. JSON에는 첫 질의, 준비 후 중앙값, 전체 질의 시간, 색인 상태와 검증 결과가 남는다.

실제 로컬 모델 회귀 검증에는 `scripts/smoke_ai.py`와 `scripts/smoke_pdf.py`를 사용했다. 한국어 의미 검색 3건, 출처가 있는 답변, 스캔 PDF OCR·의미 검색·증분 재사용이 통과했다. 전체 단위·API 테스트 114개, 마지막 검색 SQL 정렬 변경 후 검색 테스트 15개도 통과했다.

오프라인 wheel 빌드가 성공했고 새 벡터 검색 모듈이 패키지에 포함됐다. 개발 서버를 최신 코드로 다시 시작한 뒤 기존 예제 파일 9개·벡터 10개가 유지되는지 확인하고, HTTP API를 통해 실제 로컬 모델의 한국어 자연어 검색도 검증했다.
