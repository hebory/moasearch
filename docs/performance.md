# 대량 파일 성능 기록

[최신 Windows 배포판 v0.5.0 검증](#rust-v050)은 실제 폴더의 빈 DB 최초 색인과 색인 중 검색을 측정한다. 아래 과거 가상 데이터·Python·CPU 결과와 조건을 구분한다.

## Rust 전환 후 측정

2026-11-12, 같은 Windows PC에서 Rust 1.97.1 MSVC의 release 빌드로 측정했다. 가상 텍스트 파일 5,000개에서 20,000청크·384차원 결정적 가짜 벡터를 생성했다. 모델 추론·모델 로드·OCR 시간은 제외한다. 아래 Python 측정과는 색인 문서 길이와 임베딩 생성 조건이 달라 직접적인 배속 비교를 하지 않는다.

| 측정 | Rust |
|---|---:|
| 최초 색인 5,000개·20,000청크 | 8.409초 |
| 변경 없는 재색인 | 0.284초 |
| 50개 수정 후 재색인 | 0.345초 |
| 첫 검색, 벡터 캐시 준비 포함 | 110.25ms |
| 이후 서로 다른 질의 4개의 중앙값 | 8.58ms |

최초 5,000개, 수정 후 50개만 색인했고, 변경 없는 5,000개는 모두 재사용했다. 오류는 0개이며 검색 5건의 예상 첫 결과를 확인했다. 가짜 벡터 검색 검증 질의는 파일명·문서 번호·본문 단어와 겹치지 않게 구성했다. 실제 자연어 검색 품질은 별도의 Google 모델 검증으로 확인한다.

```powershell
.\build.ps1 -PrepareOnly
cargo run --release --locked --example benchmark -- --files 5000
```

보고서는 `.moasearch-perf/run-rust-<PID>/report.json`에 저장한다. 이번 측정은 `run-rust-43812`이며 각 색인 단계 1회, 검색 5회를 실행했다. 하드웨어·저장장치·문서·벡터 차원에 따라 결과가 달라진다.

### 초기 Rust 전환 당시 기능·배포 검증 (2026-11-12)

다음은 단일 데스크톱 앱으로 통합하기 전 Rust 구현의 과거 기록이다. 당시 HTTP API·인증 시험은 현재 앱의 통신 구조를 설명하지 않으며, 최신 Windows 앱은 앱 내부 IPC를 사용한다. 최신 테스트 수와 실측은 [v0.5.0 기록](#rust-v050)을 따른다.

- release 기본 테스트 32개와 모델을 별도로 지정하는 실제 OCR 테스트 1개를 통과했다. 경로 경계, 기존 DB 전환, 배치 원자성, 취소·증분 재사용, 정확 벡터 검색·캐시, API 인증, 한국어 문자열 처리와 포맷 읽기를 포함한다.
- Google EmbeddingGemma 2로 한국어 의미 검색 3건, Gemma 4 E2B로 문서 인용 답변 생성을 확인했다.
- 가상 문서 5개에서 HWP/HWPX 본문 검색 2건, 영수증·스캔 PDF·혼합 PDF 자연어 검색 3건을 통과했다. fixture 설명 README는 정답 정보를 포함하므로 검증 문서 집합에서 제외한다. 두 번째 색인은 5개 모두 재사용했다.
- PNG의 한국어·영어·숫자 OCR, 스캔 PDF, 손상된 표지 구조가 있는 혼합 PDF 복구, 유효한 디지털 PDF 텍스트 추출을 확인했다.
- 기존 예제 DB의 파일 9개·청크 10개·벡터 10개를 보존하고 Google 임베딩으로 다시 색인했다. 오류 0개, HTTP 자연어 검색의 첫 결과 `meeting.pdf`를 확인했다.
- Windows 기본 PowerShell의 설치 런처와 `dist/moasearch.exe` 실행을 확인했다. 앱에는 Python·Ollama가 필요 없으며 ONNX Runtime DLL 두 개를 함께 배포한다.

이 검증은 가상 문서와 CPU 실행을 대상으로 한다. 전체 PC 장기 운용, 모든 HWP/PDF 변형, 필기체 OCR, GPU 가속 또는 일반적인 답변 정확도 전체를 보장하는 벤치마크는 아니다.

## 이전 Python 측정

아래 비교표는 **Python 구현의 14단계(`7ee31b4`) 기록**이다. Rust 전환 후의 실행 속도를 뜻하지 않는다. Rust 측정은 `cargo run --release --example benchmark`로 별도 재현하며, 실제 모델 추론 시간은 이 합성 벤치마크에 포함하지 않는다.

2026-11-12, 같은 Windows PC의 일반 실행 프로세스에서 기존 버전 `8a509ab`와 개선 버전을 비교했다. 가상 텍스트 파일 5,000개, 별도 검색 색인 20,000청크·384차원을 사용했다. Python 3.12.13, SQLite 3.50.4 환경이다.

| 측정 | 기존 | 개선 후 | 기존 / 개선 |
|---|---:|---:|---:|
| 최초 텍스트 색인 5,000개 | 55.353초 | 15.988초 | 3.5배 |
| 변경 없는 재색인 | 4.599초 | 0.254초 | 18.1배 |
| 파일 1%인 50개 수정 후 재색인 | 4.976초 | 0.404초 | 12.3배 |
| 검색 캐시가 준비된 뒤 질의 중앙값 | 161.70ms | 8.35ms | 19.4배 |
| 첫 질의, 캐시 준비 포함 | 145.70ms | 175.40ms | 첫 준비 비용 증가 |
| 키워드 검색 1회 | 3.41ms | 2.20ms | 1.6배 |

각 색인 과정의 오류는 0개였다. 변경 없는 재색인은 5,000개 모두 건너뛰었고, 수정 색인은 50개만 처리했다. 모든 검색 측정에서 정해 둔 의미·키워드·파일명 결과를 찾았다. 질의는 총 5개이며, 준비 후 중앙값은 첫 질의를 제외한 서로 다른 4개 질의를 사용한다. 동일 질의 임베딩 캐시의 효과로 수치를 부풀리지 않는다.

## 측정에 포함한 것

색인은 파일 읽기·본문 추출·SQLite 저장·삭제 확인을 측정하며 임베딩 모델은 사용하지 않는다. 검색은 결정적인 가짜 임베딩을 주입하여 키워드 조회·벡터 검색·파일별 순위 계산을 측정한다. 실제 LLM 추론 시간, OCR 시간, 처음 모델을 읽는 시간, 검색용 가상 벡터 생성 시간은 이 표에 포함하지 않는다.

첫 질의는 DB에서 벡터 캐시를 구성하므로 기존보다 약 30ms 길었다. 이후 질의는 해당 행렬을 재사용한다. 추가·수정·삭제가 커밋되면 캐시를 다시 준비한다. 최초 캐시 준비와 반복 검색의 시간을 따로 확인해야 한다.

위 수치는 이 PC에서 각 색인 단계 1회, 검색 5회를 측정한 결과다. 하드웨어, 디스크, 백신, 문서 크기·종류, 벡터 차원에 따라 달라진다. 측정 환경의 파일 접근 제약으로 경로 확인 비용이 늘어난 샌드박스 수치는 최종 표에서 제외했다. 검색 캐시 준비 최적화 후 검색 부분만 같은 가상 DB에서 다시 측정했다.

## 바뀐 구조

- 색인 작업에서 DB 연결을 재사용하고, 완료된 파일을 묶어 원자적으로 저장한다. OCR·임베딩 중에는 쓰기 잠금을 유지하지 않는다.
- 상태 화면의 개수는 행 전체를 세지 않고 트랜잭션 안에서 갱신한 카운터로 조회한다.
- 파일 경로의 trigram FTS와 본문 조회용 인덱스로 짧은 검색어도 큰 벡터 BLOB을 읽지 않고 확인한다. 이 보조 인덱스는 추가 디스크 공간을 사용한다.
- 모델·차원·DB 변경 버전을 키로 정규화 벡터를 재사용한다. 보관하는 배열은 기본 128 MiB까지이며, 전체 프로세스 메모리 제한을 뜻하지 않는다.
- 캐시 한도를 넘거나 메모리가 부족하면 256개씩 벡터를 읽고 필요한 상위 파일 수만 유지한다. 근사 검색으로 결과를 생략하지 않는다.
- 최근 질의 64개의 임베딩을 모델별로 구분해 재사용하고, 결과 본문은 한 번의 SQL로 읽는다.

캐시는 실행 중인 앱 메모리에만 유지한다. 앱을 다시 시작하면 첫 검색에서 준비하며, 모델이 바뀌면 이전 벡터를 섞지 않는다. 백만 개 이상의 벡터, 전체 PC 장기 색인, 대규모 OCR 문서 성능은 이번 측정 범위가 아니다.

## 이전 Python 측정 재현

다음 명령과 Python 스크립트는 `7ee31b4` 체크아웃에서만 사용한다. 현재 Rust 버전에서는 Python 런타임과 스크립트를 제거했다. 각 실행은 `.moasearch-perf/run-*`에 가상 파일과 독립 DB를 만들며 사용자 문서 폴더를 읽지 않는다.

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_performance.py --label after --files 5000 --chunks 20000 --dimension 384 --repeats 5
```

같은 스크립트와 인자로 기준 버전의 `src`를 별도 체크아웃해 `PYTHONPATH`로 지정하면 기존 버전을 측정할 수 있다. `--label`은 보고서 이름만 지정하며 코드 버전을 바꾸지 않는다. 가상 파일 생성·벡터 생성 시간은 측정 구간 밖이다. JSON에는 첫 질의, 준비 후 중앙값, 전체 질의 시간, 색인 상태와 검증 결과가 남는다.

실제 로컬 모델 회귀 검증에는 `scripts/smoke_ai.py`와 `scripts/smoke_pdf.py`를 사용했다. 한국어 의미 검색 3건, 출처가 있는 답변, 스캔 PDF OCR·의미 검색·증분 재사용이 통과했다. 전체 단위·API 테스트 114개, 마지막 검색 SQL 정렬 변경 후 검색 테스트 15개도 통과했다.

오프라인 wheel 빌드가 성공했고 새 벡터 검색 모듈이 패키지에 포함됐다. 개발 서버를 최신 코드로 다시 시작한 뒤 기존 예제 파일 9개·벡터 10개가 유지되는지 확인하고, HTTP API를 통해 실제 로컬 모델의 한국어 자연어 검색도 검증했다.

실제 폴더 검증은 사용자가 선택한 파일명 전용 정책과 기존 부분 색인을 활용한 완료 검증이다. 전체 파일을 빈 DB에서 처음부터 처리한 시간은 측정하지 않았다. 검색 시간은 모델 로드를 포함한 별도 CLI 프로세스 1회씩의 소요 시간이며 UI 내부의 준비된 모델·질의 캐시 측정값과 구분한다. 실제 경로·원문과 상세 감사 JSON은 무시 경로에만 보관하고 릴리스에 포함하지 않는다.

병렬 처리 실험은 `MOASEARCH_EMBEDDING_MODEL`에 고정 GGUF 경로를 지정하고 `cargo run --release --locked --example benchmark_embedding_threads`로 재현한다. 자동 회귀는 Rust 69개와 화면·IPC 16개가 통과했다.

| 목표 파일명 첫 관측 | 주기적으로 검색한 기존 목표 파일 | 1.56초에 관측 |

| 최초 색인 전체 완료 | 본문·벡터 각 13,441개 | 443.20초(7분 23초), 오류 0개 |
| 색인 중 파일명 검색 | 493회, Rust 검색 호출 | 중앙값 0.80ms, P95 12.56ms, 최대 23.49ms |
| 본문 준비 후 GPU 색인 중 자연어 검색 | 두 응답 시간 합계, 438회 | 중앙값 68.46ms, P95 143.95ms, 최대 455.24ms |
| 전체 최초 색인 구간의 자연어 검색 | 본문 추출·OCR 구간 포함, 두 응답 합계 493회 | 중앙값 71.08ms, P95 716.81ms, 최대 2,470.95ms |
| 완료 후 같은 자연어 질의 | 기존 질의 6개, 마지막 벡터 캐시 갱신 포함 | 11.88~115.95ms |
| 변경 없는 재색인 | 별도 최종 CLI 프로세스 시작 포함 | 3.92초, 14,074개 건너뜀·저장 0개·오류 0개 |
| 실제 파일 시스템 대조 | 경로·크기·수정 시각·리더를 DB와 비교 | 누락·변경·추가·오류 0건, `quick_check=ok` |
| 파일명 전용 정책 | `_site`, `temp`, `vendor` | 12,248개 이름 보존, 해당 본문·벡터 0개 |
| 자연어 관련성 | 미리 정한 실제 기능 질의 6개 | 관련 원본 파일 또는 소개 문서 순위 1·5·1·2·1·1 |

실제 네이티브 로더에서 `load_tensors: offloaded 25/25 layers to GPU`를 확인했다. CUDA Toolkit 경로를 PATH에서 뺀 배포 실행 파일로도 이미지·스캔 PDF·HWP/HWPX 예제를 색인하고 검색했다. `CUDA_VISIBLE_DEVICES=-1`로 장치를 숨겼을 때 같은 앱이 CPU로 전환해 의미 검색하는 것을 화면에서 확인했으며, EXE와 CUDA DLL 세 개의 필수 import에 `nvcuda.dll`이 없음을 확인했다. 물리적으로 NVIDIA 드라이버가 없는 새 Windows VM에서 수행한 시험은 아니다.

자연어 검색은 먼저 `instant` 결과를 표시하고 같은 입력으로 `hybrid` 결과를 추가한다. 표의 자연어 시간은 이 두 Rust 호출의 시간을 더한 값이며 UI의 입력 debounce·IPC·화면 렌더 시간은 제외한다. 본문 준비 중에는 내용을 계속 추가하므로 문자 후보 캐시가 무효화되고 긴 질의가 느려질 수 있다. 임베딩이 끝나지 않은 문서의 의미 결과는 아직 없으며 순위도 완료 전후에 바뀔 수 있다. 관련성 평가는 전체 완료 후 결과다.

질의는 실제 기능을 바꿔 말한 사전 지정 6개를 순환하며, 각 순회 뒤 750ms를 쉰다. 반복 질의의 캐시가 포함되므로 위 값을 처음 보는 모든 자연어 질의의 응답 시간으로 해석하지 않는다. 모델·질의 임베딩이 준비된 상태의 검색과 새 모델을 처음 읽는 비용을 구분한다. 시작 전 모델 SHA-256 검증·다운로드·개발 빌드 시간은 색인 시간에 포함하지 않으며, 색인 중 실제 모델 로드와 OCR은 포함한다. 컴파일 작업은 측정 중 실행하지 않았고 디스크·OS 캐시와 다른 데스크톱 앱 부하는 통제하지 않았다.

본문 조회 재사용 전 같은 파이프라인의 빈 DB 실행도 별도로 완료했다. 전체 색인 472.39초, 파일명 등록 3.31초, 완료 후 관련 문서 순위는 동일했다. 조회 캐시를 적용해 GPU 벡터만 갱신할 때 이름·본문 후보를 다시 읽지 않게 했다. 두 실행의 OS 캐시와 질의 처리량이 달라 전체 색인의 정확한 배속 비교로 사용하지 않는다.

### 재현

`examples/benchmark_index_pipeline.rs`는 지정한 실제 폴더를 읽되 별도 데이터 폴더와 보고서를 사용한다. 시나리오 JSON에는 `filename_query`, `filename_expected`(경로 배열), `queries` 배열을 지정한다. 각 질의는 `id`, `query`, `expected`(허용하는 관련 원본 경로 배열)를 가진다. 모든 보고서·시나리오·데이터 경로는 대상 폴더 밖에 둔다. `--resume`은 같은 단일 폴더로 만든 측정 DB의 반복 측정에만 쓴다.

```powershell
. .\build.ps1 -PrepareOnly
cargo run --release --locked --features gpu --example benchmark_index_pipeline -- `
  --root 'D:\자료' --data '.moasearch-benchmarks\fresh\data' `
  --model '.moasearch-rust-dev\models\embeddinggemma-2-Q8_0.gguf' `
  --scenarios '.moasearch-benchmarks\scenarios.json' `
  --report '.moasearch-benchmarks\fresh\report.json' --expect-backend CUDA
```

데이터·보고서의 상위 폴더와 OCR 모델을 먼저 준비한다. 모델 SHA-256, 전체 완료 상태, 실제 의미 결과, 관련 문서 상위 5개와 요청한 backend가 모두 맞아야 성공한다. 취소 기한은 진행 중 네이티브 호출이 끝나기를 기다리는 종료 요청이며 강제 프로세스 제한 시간이 아니다. 실제 경로·원문·질의별 상세 보고서는 무시 경로에만 보관하고 배포하지 않는다.

자동 회귀는 **Rust 83개와 화면·브리지 24개**가 통과했다. 화면 검증에는 의미 검색 대기 중 방향키 선택·Enter 열기와 오래된 검색 결과의 열기 방지를 포함한다. 별도 실제 OCR 회귀, 512·4,096 컨텍스트의 긴 입력·혼합 길이 GPU 임베딩, 답변 옵션을 켠 격리 예제의 Gemma 4 문서 근거 답변도 확인했다.

목록형 UI를 포함한 최종 Windows 설치 파일로 실제 설치를 갱신했다. 기존 사용자 데이터의 파일 14,082개·본문 조각 및 벡터 각 13,450개와 설정이 보존됐다. 별도 측정 폴더 외에 기존 예제 위치 8개 파일도 등록되어 있어 위 빈 DB 표의 수와 다르다. 설치 앱에서 실제 폴더의 자연어 관련 결과와 미리보기, Ctrl+F·F3 검색 이동, Ctrl+Enter 탐색기 위치 표시, 탐색기 빈 공간의 ‘모아검색으로 여기서 검색’과 해당 폴더 범위를 확인했다. 범위 창을 닫으면 다른 창을 유지하고, 마지막 표준 닫기(X) 후 확인창 없이 실제 GUI 프로세스가 종료됨을 확인했다.

최종 ZIP의 766개 파일과 설치 payload 765개를 manifest의 크기·SHA-256과 대조했다. WebView2 bootstrapper는 설치 시 임시 실행하는 파일이므로 설치 폴더에는 남기지 않는다. 기존 설치에 남아 있던 이전 HTTP 의존성의 라이선스 텍스트 10개는 Cargo 캐시 원본과 해시가 같음을 별도 확인했고, 현재 실행 payload로 포함하지 않았다.
